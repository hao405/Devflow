# 会话记忆与 MemoryHub（v1.0.1）

用户连续排查 CI 时，希望系统记住已确认的原因，也能找回之前说过的原话。项目通过数据库保存记录，再按当前问题选择内容进入模型上下文。记忆不是模型调用之间自动保留的信息。

## 1. 不同对象保存什么

| 对象 | 可以怎样理解 | 保存内容 |
| --- | --- | --- |
| `Conversation` | 一个聊天窗口 | 标题、所属仓库、状态 |
| `ChatMessage` | 一条聊天记录 | 用户原文、助手回答、相关元数据 |
| `ChatSession` | 一轮问答的封存档案 | 输入输出、工具事件、摘要和诊断信息 |
| `ConversationMemory` | 当前聊天窗口的工作笔记 | 摘要、事实、决策、待办、偏好等 |
| `MemoryCandidate` | 待审核的项目记忆 | 从对话中提取出的事实、决策等候选 |

`ThreadMemory` 是没有具体会话时的回退路径，不能把它与当前聊天窗口的 `ConversationMemory` 混为一谈。

## 2. 一次请求怎样读写记忆

请求到达后，`ContextAssembler.assemble()` 读取最新压缩边界、当前会话记忆、最近封存摘要、近期消息和相关证据，按预算生成 `system_context` 与 `history_messages`。模型实际看到什么，还取决于 ChatAgent 后续如何组装提示词；数据库有记录不代表全部都会发给模型。

回答完成后，外层路由调用 `SessionSealer.seal()`，先建立本轮问答与工具事件的封存记录，再提取摘要与结构化记忆。提取失败会回退到规则结果；记忆增强失败会记录告警，不应把它当作聊天回答必然失败。

源码：[上下文组装](../backend/app/services/chat_memory.py#L469)、[一轮问答封存](../backend/app/services/chat_memory.py#L1074)、[更新结构化记忆](../backend/app/services/chat_memory.py#L1274)。

## 3. 三个记忆工具怎样选择

MCP 是连接工具调用方与工具服务的一套接口约定。项目通过它暴露三类读取能力：

| 工具 | 适合的问题 |
| --- | --- |
| `devflow_search_evidence` | 历史决策、项目资料和持久记忆有哪些？ |
| `devflow_get_thread_context` | 当前会话之前那句话的原文是什么？ |
| `devflow_read_session_events` | 某轮封存记录做过什么、调用过哪些工具？ |

最近消息已包含完整原话时，可以直接回答；超出窗口、内容被压缩或需要逐字核实时，再读原始记录。封存工具支持是否携带 transcript（原始记录），具体实现还支持字符偏移读取。这里是摘要与原始记录的不同读取粒度，没有统一的 L0 摘要、L1 章节、L2 原文档三级体系。

源码：[原始聊天读取](../backend/app/services/chat_memory.py#L1344)、[封存记录读取](../backend/app/services/chat_memory.py#L1450)。

## 4. 长期记忆为什么有审核

会话工作记忆会自动更新；从事实、决策、待办、偏好等内容中提取的项目记忆候选，先进入 `pending` 状态。候选经批准后，这条审核路径才把它写为 `memory_note`，参与项目知识检索。不能把自动生成的会话摘要说成已经审核的项目事实。

源码：[生成候选](../backend/app/services/memory_hub.py#L123)、[批准并写入知识](../backend/app/services/memory_hub.py#L178)。

## 面试口述版

> 项目把原始对话、单轮封存档案、会话工作记忆和长期记忆候选分开保存。每次请求按问题和预算重建上下文，必要时通过工具回查原话；回答后更新摘要和结构化记忆。长期候选通过审核后再进入项目知识检索。这样兼顾上下文成本和可追溯性，但摘要仍可能遗漏信息，持久化也不代表模型自动看到全部内容。

本章依据源码核对；v1.0.1 的 224 项后端测试通过不等于真实模型、数据库与 GitHub 的端到端验证完成。
