## 1. 上传：接收原文件并登记任务

当前 RAG 页面调用的接口是：

```
POST /api/rag/repositories/{repo_id}/documents
```

接口会：

1. 检查所属仓库是否存在。
2. 限制上传文件不超过 12 MB，并检查扩展名。
3. 对文件内容计算 SHA-256，同一个仓库里已有且状态不是 `failed` 的相同文件会返回现有记录。
4. 把原文件写到上传目录。
5. 在 PostgreSQL 的 `knowledge_source_documents` 表登记文件信息和 `queued` 状态。
6. 返回 HTTP 202，然后安排后台处理。

这里的 202 表示“任务已接收”。网页可以通过文档列表查看状态；完整处理后状态才会到 `completed`。

## 2.解析文件成可处理的文本，调用提取文本的函数
后台处理状态依次为 `queued`、`parsing`、`splitting`、`embedding`、`completed`；处理异常时记录 `failed`。
 pdf：用 pypdf 逐页提取文本，保留成页码标记
 DOCX：提取段落表格；标题样式转成 Markdown 标题，列表转成列表格式，表格转成 Markdown 表格。
最多限制文本为 400w 字符，且文件最大 12MB

## 3.切分
Markdown、MDX：按标题、段落和代码块等结构切片，保留章节路径与行号。PDF、DOCX 虽在提取阶段生成文本或 Markdown 风格内容，当前仍按原文件后缀走普通文本切片；这条分支的章节路径为空、page 为 None，不能声称已经完整保留章节和页码。见 [切片入口](../backend/app/services/rag/chunking.py#L761)与[普通文本切片](../backend/app/services/rag/chunking.py#L438)。
JSON：按顶层键或数组元素拆分
CSV：优先按行拆分，片段中带上表头，并带上起止行号

4.embedding
切片标题按 `section_title`、页码或 `Chunk N` 选择标签，再与文件名组合。Embedding 实际输入为标题与片段正文；不是整份文档的全部上下文。
标题和文章上下文也参与向量计算






5.入库：PostgreSQL 保存 chunk 原文；启用 Milvus 时，另外保存向量索引。Milvus 以 `Document.id` 作为主键，写入 `repo_id`、`source_type`、`source_id`、标题、正文、元数据和 embedding。向量字段使用配置维度；索引使用 COSINE 度量。

| 存储位置       | 保存内容                             | 用途             |
| ---------- | -------------------------------- | -------------- |
| 文件目录       | 上传的原始文件                          | 后续重新处理、查看来源    |
| PostgreSQL | 文件处理记录，以及每个 chunk 的标题、正文和元数据     | 状态跟踪、正文读取和来源管理 |
| Milvus     | 每个 chunk 的向量，以及仓库、文档、标题、正文和元数据字段 | 向量相似度搜索        |
6.入库之后怎么用到 chunk

# 一次查询怎样经过混合检索，变成带引用回答

1. 先确定范围，生成问题向量，入库时的 embedding 把问题也编码成向量，并限定当前只搜索本仓库，设置 topk 默认为 5
2. 分成两条路检索，向量路和关键词路，Milvus 路比较问题向量和 chunk 向量，关键词路遍历当前仓库的文档，用 BM25 给关键词打分，标题有更高的权重
3. **第一次排名。** 同一个 chunk 被两路找出时，系统按 `chunk_id` 合并。两路分数各自归一化，再计算 `0.62 × 向量分数 + 0.30 × 关键词分数 + 0.08 × 双路命中奖励`，给出具体分数
4. Rerank：一般情况：qwen rerank：接收原问题，每个候选的标题，路径，正文发给 rerank 接口。
   情况 B:qwen 调用失败或者设定为启发式重排，项目会明确使用代码中的规则重新打分
5. 编号并生成回答

### 面试时可这样复述

用户向某个仓库知识库提问后，我们用与入库一致的 embedding 模型编码问题，同时做 Milvus 向量召回和基于 Document 的 BM25 关键词召回。两路候选按 chunk 合并、加权打分、去重，再交给 rerank 精选。对命中的 chunk，我们补充同一父片段的相邻内容，经过分数门槛、证据压缩和证据检查。最后后端为证据编号，把编号片段交给模型生成回答，并随响应返回编号对应的来源，方便用户核对。

## RAG 常见面试问题（精简版）

### 1. 用户上传 PDF 后，解析、分片、向量化和存储的流程是怎样的？

流程：**完整文件上传 → 校验与去重 → 原文件落盘、任务登记 → PDF 提取文本 → 切片 → Embedding → 入库。**

1. **接收文件**：前端通过 `FormData` 上传到 `POST /api/rag/repositories/{repo_id}/documents`。后端检查仓库、扩展名及文件大小，用 SHA-256 查询同仓库内非失败的重复记录。
2. **登记任务**：原文件写入上传目录，PostgreSQL 的 `knowledge_source_documents` 表保存文件信息及 `queued` 状态。接口返回 HTTP 202，并安排进程内后台任务；202 表示已接收，不代表已完成索引。
3. **解析文本**：后台用 `pypdf` 逐页提取文字，插入页码标记。当前限制文件 12 MB、PDF 500 页、提取文本 400 万字符；没有接入 OCR（图片文字识别），纯扫描件可能无法提取有效文本。
4. **切片**：`chunk_document()` 根据页码、段落和可识别的标题等结构切分，再按长度限制拆分过长内容。知识库默认上限为每片 800 字符，重叠参数为 100 字符，可配置；并非固定按 800 字符生硬截断，也不保证每两片都重叠 100 字符。元数据保留页码、章节路径、父片段 ID 和提取文本中的行号。PDF 标题是否可识别取决于提取结果。
5. **向量化**：把每片的“标题 + 正文”送入 Embedding 模型（将文本编码为数值向量），外层每批最多 64 片，使用知识库配置的模型和维度。
6. **分工存储**：文件目录保存原 PDF；PostgreSQL 的 `documents` 表保存各片标题、正文和元数据；启用 Milvus 时，以 `Document.id` 关联保存向量及检索字段，使用 COSINE 相似度索引。流程正常结束后标记 `completed`，捕获异常时标记 `failed` 并记录错误。

状态流转：`queued → parsing → splitting → embedding → completed`；后台处理捕获异常后转为 `failed`。

### 2. 大文档上传时网络中断，如何保证可以恢复？

**当前实现：单次请求上传整个文件，尚未实现断点续传。** 这里要区分“上传文件分块”和“上传后把文本切片”，二者解决不同阶段的问题。

| 中断或失败发生的位置 | 当前处理方式 |
| --- | --- |
| 文件尚未完整传到服务器 | 需要重新上传整个文件，没有已上传分块的进度可供续传。 |
| 服务器已落盘、提交文档记录，但前端没收到响应 | 先查询文档列表和状态；重新完整上传时，SHA-256 查询可复用同仓库内非失败的已有记录，但这仍不是断点续传。 |
| 文件已保存，解析或向量化失败 | 调用 `POST /api/rag/repositories/{repo_id}/documents/{document_id}/retry`，读取已保存的原文件重新处理；不会从失败的 Embedding 批次接着执行。 |

**如果扩展为大文件断点续传，建议增加以下能力（尚未实现）：**

1. **创建上传会话**：服务端返回 `upload_id`，登记仓库、文件大小、文件哈希、分块大小和总块数，并相应调整当前 12 MB 限制。
2. **分块上传并持久记录**：前端按固定大小分块；服务端校验块哈希，先可靠保存块文件，再记录已完成的块编号。以 `(upload_id, part_number)` 保证重复提交同一块不会重复写入，内容冲突时拒绝覆盖。
3. **重连后补传**：前端保存会话标识，恢复网络后向服务端查询已完成的块，只补传缺失块；本地进度不能代替服务端确认。
4. **完整校验再合并**：全部块到齐后按编号合并，校验总大小和整文件哈希，原子发布完整文件；合并完成接口也需要防止重复创建解析任务。
5. **可靠触发后续处理**：使用持久化任务记录或事务发件箱配合任务队列，让合并成功与解析任务提交可恢复，并支持失败重试、超时任务回收和过期分块清理。当前进程内 `BackgroundTasks` 本身不提供宕机后的持久恢复保证。

口述要点：**当前已有文件去重和处理失败重试；真正的断点续传需要上传会话、分块持久化、进度查询、缺块补传和最终校验。**

源码：[前端整文件上传](../frontend/app/rag/page.tsx#L163)、[后端接收与去重](../backend/app/api/routes/rag.py#L179)、[重新处理接口](../backend/app/api/routes/rag.py#L262)。

### 3. 为什么使用向量数据库，而不只使用关键词检索？

用户的问题与文档用词可能不同。例如用户问“上传断了怎么办”，资料写的是“分块上传与断点续传”，单靠词面匹配可能漏掉相关内容。Embedding 模型提供语义表示，Milvus 负责对这些向量建立索引并检索相近片段；语义效果仍取决于模型，不能保证每次都准确。

| 检索方式 | 适合解决的问题 | 局限 |
| --- | --- | --- |
| BM25 关键词检索 | 函数名、错误码、配置项等明确词语的匹配 | 问题与资料用词不同时可能漏召回 |
| 向量检索 | 同义表达、自然语言描述与文档之间的语义匹配 | 对精确标识符可能不敏感，也可能召回语义接近但无关的内容 |

因此项目默认使用 **Milvus 向量召回 + BM25 关键词召回的混合检索**：按片段合并候选，两路分数各自归一化，以 `0.62 × 向量分数 + 0.30 × 关键词分数 + 双路命中奖励（0.08）` 融合，再按配置重排（Rerank：对候选相关性重新排序）。BM25 当前由应用读取 PostgreSQL 中的片段后计算，不是直接调用 Milvus 的全文检索。

代价是增加向量生成、索引存储及维护成本；更换 Embedding 模型时需要重建对应索引。采用混合检索的理由是让两种匹配能力互补，实际效果仍需通过同一评测集对比关键词、向量和混合检索来验证。
