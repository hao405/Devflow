**压缩真正生效，靠的是 `compact_boundary` 和后续读取规则。**

源码在 [_insert_boundary() (line 900)](../../backend/app/services/chat_memory.py#L900)。

它往数据库新增一条记录：

```
ChatMessage(
    role="system",
    content=summary,
    route="context_compaction",
    meta={
        "subtype": "compact_boundary",
        "preserved_message_ids": [...],
        "transcript_ref": {...},
        "rehydration": {...},
    },
)
```

几个字段分别表示：

- `content`：压缩摘要。
- `preserved_message_ids`：还需要继续保留哪些近期原消息。
- `transcript_ref`：需要精确原文时，去哪里恢复。
- `rehydration`：恢复工作状态的线索，例如近期文件、Skill、工具。

`rehydration` 可以理解成“把工作现场重新摆好”，帮助 Agent 知道之前操作过什么。

之后 [MessageStore.recent() (line 76)](../../backend/app/services/chat_memory.py#L76) 构造：

```
projected = [boundary, *preserved_rows]
projected.extend(rows_after_boundary)
```

也就是：

```
压缩摘要
+ 被引用的近期原消息
+ 压缩边界之后的新消息
```

例如：

```
数据库原文：
m1 → m2 → …… → m20

当前有效上下文：
摘要 → m13 → …… → m20

继续聊天：
摘要 → m13 → …… → m20 → m21 → m22
```

旧聊天原文没有被删除。近期消息也是通过 ID 引用原记录，不需要复制一份。

组装器会把边界摘要放进 `system_context` 的 `[Compaction Boundary]` 区域；历史消息则继续放在单独的 `history_messages` 中。

需要核对更早原话时，可以通过 `devflow_get_thread_context` 读取原始记录。
