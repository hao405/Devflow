# DevFlow AI 是怎样驾驭 Agent（核心精简版）

DevFlow AI 面向 Issue（问题单）、PR（代码合并请求）和 CI（持续集成检查）的研发协作。“驾驭 Agent”指的是：让模型理解问题、提出下一步，再由应用代码组织信息、执行工具、限制运行范围，并保留可检查的结果与过程。

## 1. 模型判断，程序组织执行

ChatAgent（对话 Agent）可以选择已注册工具，根据返回结果继续检索或分析。后端负责准备上下文、检查调用、执行函数、记录失败和决定何时停止。用户则明确任务目标，审阅需要确认的计划或操作草稿。

项目有两层编排：

- **对话循环**：LangGraph（状态图编排框架）连接模型决策、工具执行和预算停止节点，管理一轮对话如何推进。
- **工程工作流**：`WorkflowOrchestrator`（工作流协调器）按照明确的任务与依赖，组织多个专项分析，检查结果后汇总建议。

源码：[对话状态图](../backend/app/services/agents/chat_agent.py#L396)、[工作流执行循环](../backend/app/services/agents/workflow_orchestrator.py#L41)。

## 2. 具体控制哪些环节

| 控制点   | 项目怎样落地                               | 解决什么问题       |
| ----- | ------------------------------------ | ------------ |
| 可见信息  | 按仓库和会话组装历史、记忆与检索证据，按预算压缩             | 控制上下文范围与长度   |
| 可用能力  | 注册工具；显式 Skill（任务技能包）执行前检查工具白名单       | 限制本次调用能执行什么  |
| 任务分工  | Issue、PR、CI 专用 Agent 输出各自的分析；工作流管理依赖 | 让不同职责有明确输入输出 |
| 运行边界  | 决策轮数、重复调用、超时和补规划都有上限                 | 控制循环与失败传播    |
| 结果检查  | 专项输出校验、规则兜底、Observer（结果检查者）检查证据与冲突   | 发现部分格式和业务问题  |
| 外部写入  | 先保存安全草稿，由独立确认接口检查权限和状态               | 把操作建议与实际写入分开 |
| 回看与评测 | 保存工具轨迹、回答与会话；评测检查证据、工具行为和质量          | 支持排查问题与修改后回归 |

其中，发给模型的工具观察是经过预算处理的视图，运行状态中存在某个字段，并不意味着它一定进入模型输入。Skill 的普通说明负责引导，实际阻断还要依赖执行路径中的检查。

源码：[上下文组装](../backend/app/services/chat_memory.py#L463)、[工具观察预算](../backend/app/services/agents/chat_agent.py#L1477)、[执行前检查](../backend/app/services/agents/chat_agent.py#L733)。

## 3. 用一次合并判断串起控制链

用户明确提出“评估 PR #86 能否合并”后，对话可调用工程工作流：

```text
确定仓库、目标与可用证据
    ↓
Planner（规划者）生成包含任务和依赖的计划
    ↓
协调器执行仓库检查，调度 PR 审查、CI 诊断等任务
    ↓
Observer 检查失败、证据缺口与跨 Agent 冲突
    ↓
符合条件时有限补规划 → Synthesis（综合者）汇总建议 → 保存轨迹
```

Planner 当前按预设条件选择任务，Observer 按规则检查，Synthesis 根据结果组织报告。它们分别承担规划、检查和综合职责，并不意味着每个角色都在自主调用模型推理。

普通工具循环默认最多 **12 轮模型决策**，相同工具和参数累计请求超过 **2 次**会停止。工作流只调度依赖已成功的任务，单任务有超时，依赖失败的下游会跳过；补规划默认最多 **1 次**，配置上限为 **2 次**，新旧任务图相同也会结束。**结束时仍可能有失败、阻塞或缺失证据。**

源码：[循环预算配置](../backend/app/services/agents/chat_agent.py#L107)、[依赖调度](../backend/app/services/agents/workflow_orchestrator.py#L154)、[补规划上限](../backend/app/services/agents/workflow_orchestrator.py#L297)。

## 4. 怎样知道控制是否有效

执行中，SSE（服务端事件推送）展示工具与回答事件；正常收尾时保存答案、调用与过程记录。真实 Agent 评测再结合硬规则和模型评分，检查检索证据、工具行为与回答质量。流程记录和评测结果用于检查效果，不能直接证明所有任务都可靠完成。

当前仍有明确边界：显式 Skill 的工具限制不等于所有指令都有强制保障；Observer 只能覆盖已编写的检查；补检索后也不会自动重跑已成功的专项分析。外部写入虽然有确认接口，身份权限仍是演示实现，目标绑定与并发幂等还需完善。项目也尚未形成自动修改源码、测试和发布的完整流程。

源码：[轨迹与回答保存](../backend/app/api/routes/chat.py#L1695)、[评测通过判定](../backend/app/services/evals/ragas_runner.py#L842)、[写入确认](../backend/app/api/routes/action_drafts.py#L157)。

## 面试口述版

> DevFlow AI 通过应用代码组织 Agent 的工作。模型理解请求、选择下一步，后端管理上下文、注册工具、执行检查和运行预算。ChatAgent 负责对话工具循环，跨领域问题交给工作流按依赖调度，再检查证据、失败和结论冲突。过程通过事件和持久化记录留痕，修改后可以用评测做回归；外部写入走独立草稿确认。当前这些机制提供了可控制、可检查的执行框架，具体可靠性仍取决于规则覆盖、证据质量和实际验证。

以上依据当前源码整理，本次未运行真实模型、GitHub 或部署环境的端到端验证。
