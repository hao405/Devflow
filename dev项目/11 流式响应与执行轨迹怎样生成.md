# 流式响应与执行轨迹怎样生成（核心精简版）

用户问“最近 CI 为什么失败”时，后端既要返回最终答案，也要记录检索、工具调用和异常等过程。项目在执行过程中生成结构化事件，选择其中一部分实时发送，收尾时再保存回答与轨迹。

## 1. 先区分三类运行数据

| 数据 | 保存什么 | 主要用途 |
| --- | --- | --- |
| `agent_events` | 带 `type`、`step` 等字段的过程事件 | 记录工具调用、重试、停止原因等 |
| `tool_calls` | 工具名、参数、执行状态、错误和调用 ID 等 | 汇总各次工具调用的执行情况 |
| `stream_events` | 节点返回的、等待转发的事件 | 让流式适配器向外发送本批事件 |

`_append_agent_event()` 把事件追加到当前状态中的 `agent_events`。**记录事件与发送事件是两个动作**：一些过程信息只保留在轨迹中，随最终结果一起返回，不会立即单独推送。

源码：[追加过程事件](../backend/app/services/agents/chat_agent.py#L1461)、[转发节点事件](../backend/app/services/agents/chat_agent.py#L418)。

## 2. 一次工具调用怎样生成轨迹

进入 LangGraph（状态图编排框架）工具循环后，主要经过四步：

1. **模型提出调用**：`model_decision` 节点取得工具名、参数和调用 ID。模型同时返回可见说明时，生成 `thought` 事件；它不是完整内部推理过程。
2. **工具开始**：流式适配器观察到 `tool_action` 节点启动，根据待执行调用发送 `tool_use` 预览。节点内的 `_prepare_tool_call()` 再把对应调用记录加入轨迹。
3. **执行与检查**：`_complete_tool_call()` 检查工具和显式技能约束，再调用执行函数。失败会记录错误类型；符合重试条件时，还会追加 `tool_retry` 事件。
4. **工具结束**：生成 `tool_result`，保存状态与结果摘要，并把摘要加入 `observations`（后续模型可使用的观察结果）。节点返回后，适配器向外转发结果事件。

开始事件的 `id` 与结束事件的 `tool_use_id` 对应，便于把它们关联成同一次调用。轨迹中的结果以摘要为主，不能理解成所有原始工具输出和底层执行细节。

源码：[工具调用记录](../backend/app/services/agents/chat_agent.py#L703)、[结果记录与观察更新](../backend/app/services/agents/chat_agent.py#L822)。

## 3. 事件怎样成为流式响应

`/api/chat/stream` 返回 `StreamingResponse`（流式响应），响应类型为 `text/event-stream`。内部的 `_conversation_sse()` 使用 `async for` 逐个取得 `ChatAgent.run_stream()` 产生的事件，再通过 `yield` 逐条交给响应层。

SSE（Server-Sent Events，服务端事件推送）的编码格式如下，这是格式示例：

```text
event: tool_result
data: {"tool_use_id":"call_1","tool_name":"workspace.read_file","status":"success"}

```

`event` 表示事件名称，`data` 是 JSON 数据，末尾空行表示一条事件结束。工具执行期间可以发送开始和结果事件；得到完整答案后，`_stream_answer()` 默认按每段 36 个字符生成 `delta`，最后产生带完整答案、轨迹和结束信息的 `final`。

源码：[流式接口](../backend/app/api/routes/chat.py#L1790)、[答案分段与 SSE 编码](../backend/app/services/agents/chat_agent.py#L2075)。

## 4. 最终结果与轨迹怎样保存

正常收到 Agent 的 `final` 后，接口层先生成运行 ID，保存回答与 `tool_calls`，把 `agent_events` 放入消息元数据；再创建 `AgentRun` 运行记录，通过 `SessionSealer` 把本轮消息、工具记录和事件封存到 `ChatSession.transcript_json`。数据库提交成功后，才向客户端发送这条 `final`。

历史页面可以读取已保存事件来重建轨迹。`final` 表示本轮结果返回结束，任务是否完成还要看 `completion`：它包含结束状态、原因、步骤数和工具错误数，可区分正常完成、受阻、预算耗尽等情况。

源码：[保存后发送 final](../backend/app/api/routes/chat.py#L1695)、[会话轨迹封存](../backend/app/services/chat_memory.py#L1068)、[结束信息生成](../backend/app/services/agents/chat_agent.py#L634)。

## 5. 当前实现的边界

- 当前答案是生成完整文本后分段发送，尚未实现模型逐 token（文本生成单位）输出的全链路透传。
- 确认计划执行接口会等待整个工作流返回，再转换、发送内部任务结果，任务轨迹并非全部实时产生并推送。
- 当前主要在收尾时保存轨迹，不能保证断线前每条已发送事件都已落库；历史轨迹读取也不等于流式连接支持断点续传。

源码：[普通对话收尾](../backend/app/services/agents/chat_agent.py#L369)、[工作流结果发送时机](../backend/app/api/routes/chat.py#L1518)。

## 面试口述版

> 项目在 Agent 执行时记录结构化事件，用调用 ID 关联工具开始与结果，并保留失败、重试和停止信息。流式适配器把需要实时展示的事件交给 SSE 接口发送，最终答案通过 delta 分段返回。正常收尾时，后端先保存回答和事件，再发送 final，供前端结束展示和后续历史回看。当前事件记录与实时推送并非一一对应，答案也采用生成后分段发送，工作流内部进度和断线恢复仍有完善空间。

以上依据当前源码整理，未进行真实模型与部署环境的端到端验证。
